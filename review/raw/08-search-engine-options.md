# Run 08 — Elasticsearch versus Solr

## Scope and current evidence

This is a source-based feature inventory and an experiment plan, not a measured engine comparison. The checked-out Kramerius revision and bundled Solr configuration are not matched to production. Run 01 found 377,902 client-search GETs on 2026-10-19 UTC (p50 22 ms, p95 421 ms, p99 1,926 ms) and 1,657 5xx. A [subsequent trace check](12-search-400-correlation.md) linked two peak failure windows to Solr HTTP 400 and found a deployed application status-mapping mismatch; the underlying Solr rejection reason remains unknown. The operator's report of Solr downtime may describe other incidents. The access-log `endpoint` category is manually curated. These numbers establish demand and an error-diagnosis question; they show no Elasticsearch speed advantage.

Keep three decisions separate: (1) whether the present Solr cluster and its client usage can meet the service objectives, (2) whether Elasticsearch offers a technical or operational advantage at equal functionality and resources, and (3) how to migrate if the second decision favors it. Migration effort belongs only to the third decision.

Candidate query classes for a replay set are: exact PID and identifier lookups; title/author/full-text and OCR queries; Czech diacritic and morphology cases; filtered public/CDK queries; multi-facet searches; highlighting-heavy searches; sorting and deep pagination; terms/autocomplete; and admin/report scans. Stratify by actual production frequency, result size, time of day, and cold/warm state. The current aggregate endpoint classifier does not supply those query classes; capture sanitized query *shapes* or build a representative fixture under access controls. Include indexing jobs from Run 05 and concurrent image openings from Runs 01–02, because Solr also appears in non-search request paths.

## Technical and operational comparison

| Dimension | Solr baseline | Elasticsearch possibility and tradeoff | Evidence gate |
| --- | --- | --- | --- |
| Search features and relevance | Existing query syntax, facets, terms, highlighting, and response format are native to current clients. Solr provides [faceting and highlighting](https://solr.apache.org/guide/solr/latest/). | Elasticsearch has [query-string search](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-query-string-query), [terms aggregations](https://www.elastic.co/docs/reference/aggregations/search-aggregations-bucket-terms-aggregation), and [highlighting](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/highlighting). Syntax, count accuracy, scoring, and snippet behavior are not identical by name. Terms aggregations can report approximate counts in distributed operation, so exact-count requirements need explicit tests. | Golden queries and judged relevance set; compare result IDs/order, facet values/counts, snippets, missing fields, and response transformation. |
| Analysis | Current analyzers and dictionaries are embedded in the Solr configset. | Elasticsearch supports [Hunspell](https://www.elastic.co/docs/reference/text-analysis/analysis-hunspell-tokenfilter) and [synonyms](https://www.elastic.co/docs/reference/text-analysis/analysis-synonym-tokenfilter), but chain ordering, dictionary placement, token positions, and scoring must be verified. | Compare `_analyze`-style token streams against Solr analysis for representative Czech and English terms, then relevance judgments. |
| Updates and freshness | Current add/atomic update/commit behavior and its operational costs are known in code, not timed in production. | Elasticsearch supports [partial/scripted updates](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/update-document) and bulk operations; its [refresh controls](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/refresh-parameter) govern search visibility. Frequent forced refresh can hurt throughput. | Same document mix, same visibility objective, batch size, update ordering, and retry semantics; report accepted writes separately from searchable writes. |
| Distributed availability | [SolrCloud](https://solr.apache.org/guide/solr/latest/deployment-guide/cluster-types.html) supports shards, replicas, failover and uses ZooKeeper. Actual production layout and why Solr was unavailable are not established. | Elasticsearch also shards and replicates indices ([architecture](https://www.elastic.co/docs/deploy-manage/distributed-architecture/clusters-nodes-shards)). A configured, tested failover design could improve availability, but changing engine alone cannot remove shared power, storage, client, or operational failure modes. | Run identical node, shard, network, and recovery faults; compare successful requests, degraded latency, recovery time, data loss and operator effort. Correlate existing Solr incidents first. |
| Security and operations | Solr has [authentication and authorization plugins](https://solr.apache.org/guide/solr/latest/deployment-guide/authentication-and-authorization-plugins.html) and [backup/restore](https://solr.apache.org/guide/solr/latest/deployment-guide/backup-restore.html). Current operational skill and tooling are Solr-oriented. | Elasticsearch offers [security controls](https://www.elastic.co/docs/deploy-manage/security), [snapshots](https://www.elastic.co/docs/deploy-manage/tools/snapshot-and-restore), and managed deployment options. Feature availability and support depend on [deployment and subscription](https://www.elastic.co/docs/deploy-manage/license). It adds a different operating model; managed service may reduce some operator work at a service cost. | Select concrete self-managed or managed offerings; compare patching, monitoring, backup restore drills, incident response, support terms, and total recurring cost. |
| Scaling and resource use | Solr tuning of schema, replicas, commits, caches and client batch usage may address measured limits without a replacement. | Elasticsearch may be easier for the team to run or scale for this workload, or may require more CPU/heap/disk for equivalent relevance/facets. Neither direction is established. | Same data, replica durability, query mix, index freshness, hardware/network budget and concurrency; measure CPU, heap/GC, disk, I/O, tail latency, and capacity headroom. |

The technical/operational case *for* Elasticsearch is a viable alternative set of search, aggregation, update, security, snapshot and managed-operation features. Its potential downsides are parity gaps in the required semantics, possible resource/cost differences, subscription constraints, and a new steady-state operating model. None is a measured disadvantage for this deployment yet. Code and data migration are intentionally excluded from this pros/cons comparison and specified below.

## Controlled comparison and decision gate

1. **Verify the baseline.** Record deployed Kramerius and Solr revisions, active schema/configsets, collection and shard/replica topology, JVM/resource limits, storage, commit/refresh policy, availability objective, and Solr incident timeline. Profile representative healthy and degraded search paths with runtime traces, Solr timings, GC and pool waits. Classify real queries into the shapes above without exporting user text or identifiers. Repeat Run 05 indexing measurements on the same input manifest.
2. **Build a parity fixture.** Preserve a stratified document set including Czech/English, OCR, large documents, collections, licenses, ancestor paths, updates and deletes. Prepare golden query/result snapshots plus human relevance judgments. Record which outputs require exact parity (authorization, identifiers, public API fields, facet counts) and which allow judged relevance differences. Match analyzer tokens, filters, sorting, highlights, pagination, and terms behavior. A feature without an acceptable equivalent is a gate, regardless of benchmark speed.
3. **Run equal-budget experiments.** Compare a tuned Solr baseline and Elasticsearch with the same source set, replicas/durability objective, available CPU/RAM/storage, network placement, concurrent indexing and search, and visibility target. Sweep representative concurrency and batch/commit or refresh settings. Report p50/p95/p99 search latency, successful queries/s, indexing documents/s and full job time, index visibility delay, error rates, CPU/heap/GC, disk usage/I/O, and result/relevance parity. Keep engine timings and application response transformation separate. Measure image-open time where the path calls search, and confirm no direct effect on image-server work.
4. **Test failures and operations.** Repeat node restart, shard unavailability, network partition, full disk, slow storage, client timeout/retry, backup and restore, and rolling upgrade in isolated environments. Compare success under fault, recovery time, lost/duplicate writes, index consistency, support effort, and restore objective. Price the *specified* topology over a chosen horizon, including replicas, snapshots, monitoring, licenses/support, and operator effort. Healthy speed and availability remain separate outcomes.

**First pilot:** one isolated search collection with a small representative, checksum-verified document fixture and a fixed set of exact-ID, Czech full-text, filtered facet, OCR-highlight, and update/visibility cases. The first gate is feature and relevance parity; only then run load and failure comparisons. Until measurements exist, no numerical gain for searching, indexing, or image opening is defensible. Diagnose Solr HTTP 400 reasons and any separate outage incidents before using 5xx as evidence for an engine decision.

Decision: retain and tune Solr if the current architecture meets objectives or if Elasticsearch has no measured net advantage at acceptable parity/cost; pursue Elasticsearch only if parity, end-to-end benefit, recovery, and ongoing operation clear agreed gates. A result can be mixed: different Solr collections may have different owners and requirements.

## Separate migration workstream if Elasticsearch wins

1. Inventory every Solr collection, schema/configset, query/client, update writer, direct Solr URL, response transformer, exported API shape, and index-version dependency. Assign one owner and source of truth for each index. Include processing, statistics/logs, OAI and migration tooling, or explicitly retain them on Solr.
2. Convert field mappings, dynamic fields, analyzers, dictionaries, synonyms, spatial/path fields and doc-value needs; test token and document equivalence. Design explicit translations for Solr query/local-param syntax, `fq`, facets/terms, highlighting, cursor paging, and XML/JSON response behavior. Define an API compatibility layer if clients send Solr parameters directly.
3. Build an idempotent full-reindex path from authoritative Akubra/metadata sources, then capture concurrent writes/deletes with ordered change records or a bounded reconciliation window. Do not rely solely on copying the existing Solr index as a source of truth. Check counts, per-PID checksums, rights-sensitive fields, parent paths, visibility, and relevance before cutover.
4. Dual-read or shadow representative requests without exposing Elasticsearch results to users; compare IDs, rank, facets, snippets, latency, and authorization-sensitive output. Route a reversible canary only after correctness and operations gates pass. Keep writes/reconciliation running and prove rollback to Solr after an Elasticsearch outage or mismatch. Define final cutover, monitoring, and a time-bound retirement plan for any Solr collection being replaced.

The implementing team needs deployed search topology/configuration and incident records, sanitized query-shape aggregates and traces, an authorized document/relevance fixture, representative indexing jobs, a production-like staging environment for both engines, failure-test and restore access, service objectives, and current vendor/support pricing. This run made no production changes and did not run a benchmark.
