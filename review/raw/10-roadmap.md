# Run 10 — findings index and delivery roadmap

For the next source-only design tasks, use the [priority triage](24-priority-triage.md). It groups related correctness findings into reviewable contracts without implying measured production impact.

## Decision status

The review has mapped representative source paths and a limited production workload. A [Phase 0 follow-up](11-deployment-incident-check.md) verified the gateway's public/curator route split and same deployed image digest. A [search-error check](12-search-400-correlation.md) linked two peak search-error windows to Solr HTTP 400 responses and verified a deployed exception-class mismatch that maps 400 to 500. It has **not** matched checked-out source to the image digest, verified full CDK configuration, timed dependency stages, identified why Solr rejected those queries, or run controlled staging experiments. Consequently this is a priority order for **verification and pilots**, not a ranking of measured speed gains or a recommendation to deploy a new cache, engine, storage backend, or service. The manually curated ClickHouse `endpoint` list is useful for named routes; unmatched CDK paths need explicit path-family classification.

On 2026-10-19 UTC, direct IIIF `info.json` had 61,185 GETs (p50 116 ms, p95 639 ms). Forwarded CDK `info.json` had 86,204 GETs (approximate p50 589 ms, p95 2,747 ms) and forwarded tiles had 155,597 GETs (approximate p50 625 ms, p95 2,637 ms). Client search had 377,902 GETs (p50 22 ms, p95 421 ms, p99 1,926 ms) and 1,657 5xx. Solr HTTP 400s are linked to the failing search traces in two sampled spikes; the day-wide cause and the reason for Solr's rejection remain unresolved. These counts identify exposure, not the portion removable by a particular change ([Run 01](01-baseline.md), [Run 02](02-iiif-logging.md)).

## Estimation and overlap rules

For each accepted candidate, report baseline and candidate absolute time or throughput, relative change, confidence interval or run variability, offered load, cache state, data shape, failure state and resource budget. **Indexing:** documents/s, full job duration, bytes read, NFS/Solr pressure and visibility delay. **Image opening:** route p50/p95/p99 and browser time-to-image, with direct/forwarded routes separate. **Searching:** healthy-period p50/p95/p99, successful throughput, relevance/facet parity and separate outage success/recovery metrics. A storage, rights or service-boundary change can affect search or images only if the corresponding path uses it or shared-resource contention changes; show the path/trace evidence.

For stage-removal projections, use the measured critical-path contribution as an upper bound, then subtract replacement work, contention and tail effects in the controlled test. Do not add overlapping gains: a FOXML cache and async logging might remove the same synchronous FOXML read; batching and index-writer isolation might relieve the same Solr pressure; storage compression and cached reads might both reduce the same NFS bytes. Report the combined candidate only after separate experiments. Never infer whole-repository space savings from FOXML compression alone. Use source call graphs to enumerate possible paths, runtime traces for executed dependencies and waits, aggregate logs for frequency/failures, and controlled benchmarks for causal effects.

Rollout gates for any approved change: deployed revision and owner known; correctness fixture passes including mutation/retry/restart cases; unchanged authorization and API contract where required; an end-to-end benefit or explicit correctness/availability gain under realistic load; capacity and failure behavior within service objectives; observability for error, backlog, stale data and recovery; reversible canary or dual path; documented rollback and data reconciliation. A pure bug fix can qualify on correctness without a speed gain. No rollout is requested or authorized by this review.
