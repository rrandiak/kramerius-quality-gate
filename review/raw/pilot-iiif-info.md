# Pilot: production-guided call path for IIIF `info.json`

## Evidence and scope

Read-only aggregate queries against production ClickHouse on 2026-10-20 used the complete day 2026-10-19. The NGINX table is partitioned by day and stores normalized `endpoint`, method, status, and `response_time_ms`. The `endpoint` categories come from a manually curated list, so unmatched routes can appear as `unknown`. No raw URLs, PIDs, user identifiers, or individual traces were copied into this report. Quantiles here are approximate ClickHouse `quantile` results; NGINX response time includes more than Java execution. [Run 01](01-baseline.md) contains exact quantiles for the named October 19 GET endpoints and a second-day comparison.

| GET endpoint | Requests | p50 | p95 | p99 | 5xx |
| --- | ---: | ---: | ---: | ---: | ---: |
| `/search/iiif/{pid}/{region}/{size}/{rotation}/default.jpg` | 1,287,720 | 117 ms | 628 ms | 1,307 ms | 88 |
| `/search/api/client/v7.0/items/{pid}/image/thumb` | 877,665 | 62 ms | 526 ms | 1,013 ms | 101 |
| `/search/api/client/v7.0/search` | 377,902 | 22 ms | 432 ms | 2,092 ms | 1,657 |
| `/search/api/client/v7.0/items/{pid}/info` | 68,077 | 109 ms | 694 ms | 1,482 ms | 0 |
| `/search/iiif/{pid}/info.json` | 61,185 | 116 ms | ~630 ms | ~1,200 ms | 23 |

The IIIF `info.json` route also received 51,484 `OPTIONS` requests; their p50 was 3 ms. Therefore, latency for this use case must be reported for `GET` specifically. The separate `/search/api/client/v7.0/items/{pid}/image/iiif/info.json` route did not appear as its own normalized endpoint in this day's aggregate. That absence does not prove zero traffic: the curated endpoint list may omit it. A later bounded path-family aggregate found 86,204 forwarded CDK IIIF `info.json` GETs on the same day within `endpoint = 'unknown'` (approximate p50 589 ms, p95 2747 ms). These are a distinct route family, not part of the direct servlet row above.

The trace table held 6,731,910 spans for `kramerius-public` that day, including 14,369 spans marked `STATUS_CODE_ERROR`. Span errors are not equivalent to failed HTTP requests; parent and child spans can both be marked as errors.

## Source call path

The focused [source-derived call graph](iiif-info-callgraph.svg) is generated by `review/raw/tools/build_iiif_callgraph.sh`. Solid edges are calls found in the Java AST; dashed edges mark the servlet route, a branch, a Guice binding, or a service boundary that source parsing alone cannot resolve. The underlying calls and source locations are in `review/iiif-source-calls.tsv`.

The `/iiif/*` servlet mapping is in `kramerius/search/web/WEB-INF/web.xml`; it names `cz.incad.Kramerius.imaging.IiifServlet`. The servlet has distinct CDK and non-CDK branches, so production configuration must be checked before treating the latter as the executed branch.

```mermaid
flowchart TD
    A[GET /search/iiif/{pid}/info.json] --> B[IiifServlet.doGet]
    B --> C{cdk.server.mode?}
    C -- yes --> D[proxyInfoJson to source Kramerius]
    C -- no --> E[Solr PID paths and rights checks]
    E --> F[IIIFUtils.iiifImageEndpoint via Akubra RELS-EXT]
    F --> G[reportAccess]
    G --> H[AggregatedAccessLogs]
    H --> I[SolrStatisticsAccessLogImpl]
    I --> J[read Solr document]
    I --> K[read FOXML for path ancestors]
    I --> L[write log record to Solr]
    G --> M[GET image server info.json]
    M --> N[rewrite @id and send response]
```

Source anchors: `IiifServlet.java` (`doGet`, `reportAccess`), `IIIFUtils.java` (`iiifImageEndpoint`), `AggregatedAccessLogs.java` (`reportAccess`), and `SolrStatisticsAccessLogImpl.java` (`reportAccess`). In the non-CDK path, the logging calls occur before the image server request. The logger reads the Solr document, loops through paths and loads FOXML for each distinct ancestor, and sends an update to the logs Solr collection. The number of FOXML reads depends on path depth and shared ancestors; it is not yet measured.

## Candidate and next measurement

The candidate is to capture request and user attributes on the request thread, then enqueue a bounded logging event for later enrichment and batched writes. This could remove logging I/O from response latency if the non-CDK branch is used, but no speed gain is assigned yet. The design must preserve event ordering where required, handle queue overflow and retries, and avoid holding servlet request objects or thread-local security state after the request ends.

Next, verify effective production routing for both direct and forwarded IIIF. The NGINX access table has no trace ID, so it cannot directly join individual requests to traces. A five-minute trace query found no spans named for `IiifServlet` or `reportAccess`, so current tracing may not separate those calls. Measure time in rights checks, Solr reads, Akubra reads, log writes, and the image server call with targeted instrumentation or JFR in a test deployment. Then compare logging alternatives in a non-production benchmark with equivalent workload if logging is shown to be on the critical path.

The search endpoint had 1,657 observed 5xx responses and a 2,092 ms p99 for GET on the sampled day. The user reports that search 5xx responses are primarily caused by Solr downtime. Of the 1,657 responses, 1,655 were HTTP 500 and two were HTTP 502; the errors occurred across multiple five-minute windows. This initial snapshot could not determine cause. A [later bounded trace check](12-search-400-correlation.md) linked two peak windows to Solr HTTP 400 responses and found a source exception-class mismatch that maps those responses to API 500. Why Solr returned 400, and whether other incidents reflect downtime, remain open. A full-day trace-ID join exceeded ClickHouse's memory limit; further joins must use narrow windows and explicit resource limits.
