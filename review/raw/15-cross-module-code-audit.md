# Cross-module source audit — indexing, Akubra, processing, curators

This bounded manual pass broadened Run 04 beyond search and IIIF. I used `rg` to locate error handling, resource acquisition, job completion, queue selection, and mutation/scheduling boundaries, then followed callers. Inspected source spans cover search-index model jobs and `Indexer`, Akubra object reads, process manager log proxy and worker selection, collection edits, UI config storage, rights deletion, and folder item deletion. It is **not** a repository-wide static-analysis result. No application code or production data was changed; none of the new defects has been reproduced or matched to a deployed revision.

| ID / priority | Source evidence and trigger | Effect and confidence | Focused validation / fix direction |
| --- | --- | --- | --- |
| B15 / high | `NewIndexerProcessIndexModel.java:115–158` increments `nowIndexed` whenever `indexByObjectPid` returns, and fails the job only for thrown errors or filtered items. `Indexer.java:326–340` catches per-object failures into `Counters.errors`, while `Indexer.java:137–155` clears `full_indexation_in_progress` and returns. The model-wide caller never inspects `Counters.errors` or invokes `summary`. | **Confirmed source-level accounting gap:** a failed document can leave an incomplete index while the top-level job reports it indexed, clears the retry marker, and can finish successfully. The next selective run may skip it because `indexer_version` is already current (`NewIndexerProcessIndexModel.java:187–207`). Production incidence unknown. | Inject one document failure in a tree, then assert job status, indexed/failed counts, marker, and selective retry behavior. Fail or expose partial success from accumulated counters; retain a reliable retry marker until the whole tree succeeds. |
| B16 / medium | `WorkerClient.java:112–129` opens a `CloseableHttpResponse` for log download without closing it. HTTP 404 returns `null`; `ProcessEndpoint.java:183–190` wraps that null in a 200 streaming response and calls `transferTo`. The non-200 error reports the unchanged `statusCode = -1`. | **Confirmed source-level response-lifetime and 404 handling gaps.** Connection-pool impact depends on connector behavior; a missing log can fail during streaming after a 200 response has been built. | Use a bounded HTTP pool and worker 200/404/500 fixtures; assert response/stream closure, manager status, and actual upstream status in errors. Tie the upstream response lifetime to the returned stream, or stream within a scoped response; map missing logs explicitly. |
| B17 / high | `AkubraDOManager.java:130–138,274–284` borrows an `Unmarshaller` from a pool of 50 and returns it only after successful `unmarshal`. Malformed FOXML or read failure skips `offer`; the next `take()` can block indefinitely once all 50 are lost. Both storage reads and direct unmarshalling have this path. | **Confirmed source-level pool depletion path**, conditional on repeated failures. Production incidence and whether bad objects repeat often enough are unknown. | Feed a malformed object repeatedly in an isolated repository with timeouts; assert pool size and that subsequent valid reads do not block. Return the borrowed object in `finally` (or discard and replace a poisoned instance); preserve interrupt status on interrupted waits. |
| B18 / medium | `NewIndexerProcessIndexModel.java:115–117` increments `nowIgnored` for items intentionally excluded by a selective filter, then line 161 throws if `nowIgnored > 0`. `shouldIndex` at lines 204–208 is explicitly a selection predicate. | **Confirmed source-level status mismatch:** a selective job containing any already-current or otherwise excluded model item finishes with an error even if every selected item succeeds. This is separate from B15's hidden document errors. | Run a selective model job with one eligible and one up-to-date item. Distinguish intentionally skipped items from failures; only fail on actual errors according to the job contract. |
| B19 / medium | `CollectionsResource.java:404–426` assigns `scheduleReindexationPar[0]` only when collection metadata changes; line 426 always passes it to `APIProcessScheduler.scheduleMainProcess`, whose first dereference is `scheduleReindexationPar.getString` (`APIProcessScheduler.java:25`). | **Confirmed source-level null path:** an idempotent PUT with identical metadata throws instead of returning a successful no-op. The collection itself need not be changed. | PUT an unchanged collection in an isolated fixture; assert no process is scheduled and a documented success response. Schedule only when content changes. |

Two additional bottleneck/reliability candidates merit measurement, not a speed claim. `ProcessService.java:160–176` serializes worker polls in one manager JVM and loads every PLANNED row via `ProcessDao.java:61–73` before choosing one; poll cost and worker wait could grow with backlog. Measure DB query time, planned-row count, poll wait, and schedule-to-start latency under representative queue sizes before trying a bounded or atomic DB claim. `CollectionsResource.java:405–426` writes MODS and RELS-EXT, then schedules reindexing outside the repository lock. A manager failure after the writes can leave the search index stale until reconciliation; fault-inject scheduling failure and compare repository versus Solr. This is a consistency contract to define, not evidence of a current incident. UI-config save/delete uses scoped JDBC resources (`DbUIConfigResourceService.java:27–47,95–105`), and the reviewed rights delete and folder removal entry points yielded no additional confirmed defect in this pass; B10 already covers folder count maintenance.

Priority for later validation: B15 and B17 first because they can hide or stall repository/index work; B18 and B19 next as small deterministic checks; B16 with a bounded worker log proxy check. Per the operator, no tests are being added in this review pass; execute validation in the Kramerius benchmarking environment being built separately. An attempted B17 fixture could not compile because the private build dependency was unavailable, and that fixture has been removed ([handoff](16-akubra-pool-reproduction.md)). For performance, compare complete indexing job duration and documents/s before/after B15/B17 repairs only if the work changes; compare manager poll and schedule-to-start distributions for queue changes. Collection no-op behavior and log proxy status require functional assertions, not an invented latency gain. Deployed revision matching, static analysis, and full-module test/build passes remain open.
