# Run 04 — bounded bug audit

## Scope and evidence standard

This is a targeted review of the cache and IIIF-adjacent paths reached in Runs 02–03, plus a bounded production error-span sample, a [search/logging code follow-up](14-targeted-code-audit.md), and a [cross-module source pass](15-cross-module-code-audit.md). It is not a general certification of Kramerius, Akubra, or process-platform. The checked source and deployed image revision are not generally matched, although B11's relevant deployed exception classes were verified. A source-level flaw can be definite while its production incidence remains unknown. No code or production behavior was changed.

Reviewed files: `CDKRequestCacheSupportImpl`, `CDKRequestItem`, `RightsResolverFromRequestCached`, `RightsResolverFromRequest`, `ClientApiResource`, `DCContentUtils`, `ReplicationsResource`, `AggregatedAccessLogs`, `SolrStatisticsAccessLogImpl`, direct/forwarded IIIF handlers, focused process manager/worker lifecycle paths, Akubra object write/delete/read paths, model-wide indexing, and selected curator mutations. Coverage gaps include most admin mutations, full Akubra transaction/recovery behavior, most non-IIIF endpoint resource lifetimes, and a full static-analysis/build pass.

## Production error taxonomy sample

Read-only aggregates used **2026-10-19 12:00–12:15 UTC**, `ServiceName = 'kramerius-public'`, and `StatusCode = 'STATUS_CODE_ERROR'`, grouped only by span name. Bounded query settings were `max_execution_time=30`, `max_memory_usage=1073741824`, `max_threads=2`; no trace IDs, status messages, PIDs, URLs, or users were exported. The sample returned 55 `ItemsResource.getOcrText` error spans, 55 `ClientApiResource.checkUserIsAllowedToReadDatastream` spans, 28 `ItemsResource.getImgThumb`, 24 `AkubraLowlevelStorage.retrieveObject`, and 21 `SearchResource.get` spans. Parent and child spans can represent the same request, and OTel error status can cover handled exceptions or non-5xx outcomes.

In the same UTC window, the curated NGINX endpoint list had 601 OCR-text GETs and **zero** 5xx, 9,061 thumbnail GETs and one 5xx, and 4,411 search GETs and 21 5xx. These aggregates cannot join individual requests to traces because the NGINX table has no trace ID. In particular, the 55 OCR error spans are **not** evidence of 55 failed HTTP requests. The `endpoint` classification is manually curated; `unknown` means unmatched by that list.

For the complete 2026-10-19 UTC day, search had 1,657 GET 5xx. The operator reports these are primarily associated with Solr downtime, but [follow-up trace analysis](12-search-400-correlation.md) found Solr HTTP 400s in all failing search traces of two peak windows, and 1,653 distinct Solr-400 traces across the day. Thus **do not classify that day's sampled spikes as connection downtime**. The Solr rejection reason and the two search 502s remain unknown. The sampled `AkubraLowlevelStorage.retrieveObject` error spans also need cause grouping before attributing them to NFS, missing objects, or code. Continue grouping by upstream HTTP status, timeout/connect error, expected authorization/missing object, application exception, storage/index inconsistency, and telemetry-only marking.

Use a static analyzer and a focused test/build run appropriate to each module once a finding is selected for repair. Obtain sanitized Solr rejection reasons and incident records before assigning all search 5xx to one cause. For any fix, measure correctness/availability separately from speed; compare affected route/job latency only where the fix actually changes the work performed.
