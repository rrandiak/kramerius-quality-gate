# Targeted code audit — search and request-time access logging

## Method and scope

This pass followed the two production paths established by [search error traces](12-search-400-correlation.md) and [IIIF runtime traces](13-iiif-runtime-paths.md). It inspected `SearchResource`, `SolrStatisticsAccessLogImpl`, `LogFields`, `LogRecord`, `SolrUpdateUtils`, and their immediate call sites. Searches used `rg`; Semgrep, SpotBugs and PMD are not installed in this workspace. This is a targeted manual source audit, not a repository-wide scan or a benchmark. The deployed exception mismatch B11 was separately verified in bytecode; the new findings below have not been matched to deployed classes or reproduced under load.

## Findings

| ID | Code evidence | Consequence and confidence | Small validation |
| --- | --- | --- | --- |
| B12 — access-log HTTP response lifetime and failure visibility | `SolrUpdateUtils.java:24–40` obtains a Jersey `ClientResponse` for each Solr logs POST, but never closes it. On HTTP 200 it does not consume the response entity; on non-200 it reads the body, logs it and still returns `void`. Transport/serialization exceptions are also logged and swallowed. `SolrStatisticsAccessLogImpl.java:313` calls this for request-time access logging; `SolrAPICallMonitor` also calls the helper. | **Confirmed absence of explicit response close and caller-visible failure.** Whether Jersey's connector auto-releases these particular responses, and actual pool/connection pressure, require measurement. Failed log writes can be invisible to callers and to any completeness counter; whether that violates the desired logging contract is an operator decision. | In an isolated client with a bounded connection pool, repeat successful and failed POSTs; inspect active/leased connections and response closure. Return a structured success/error result or emit reliable failure counters according to the agreed durability contract. |
| B13 — missing DC can abort log enrichment | `LogFields.java:78–93` returns `null` from `getDCCreators` and `getDCPublishers` when `BIBLIO_DC` is absent. `SolrStatisticsAccessLogImpl.java:242–248` immediately iterates both arrays without null checks. The enclosing catch handles only `SQLException` and `XPathExpressionException`; its `finally` still attempts to send the partially built log record. `AggregatedAccessLogs.java:24–30` catches any remaining throwable. | **Confirmed source-level null iteration path**, conditional on a FOXML ancestor without DC. The request may still succeed while logging emits an incomplete record or fails; production frequency is unknown. | Build a minimal FOXML fixture without `BIBLIO_DC`, call `reportAccess`, and assert the agreed behavior: complete fallback metadata or an explicit failed-log outcome. Add creators/publishers empty-array semantics or guarded iteration. |
| C1 — duplicate Solr-log XML construction | `SolrStatisticsAccessLogImpl.java:302–313` constructs a batch with `toSolrBatch`, serializes it for a FINE message unconditionally, then calls `toSolrBatch` again for the actual send. `SolrUpdateUtils.java:25–30` serializes that second document again. `LogRecord.java:413` creates a new document builder each time. | **Confirmed redundant work on every access-log call.** The logging-level check does not guard the first serialization. Absolute CPU/allocation and request-latency cost are unmeasured; the Solr POST and enrichment may dominate instead. | Use JFR/allocation profiling or a bounded microbenchmark with representative log records; compare one-batch reuse and conditional FINE formatting, then validate end-to-end IIIF latency and log equivalence under load. |
| C2 — repeated ancestor enrichment | `SolrStatisticsAccessLogImpl.java:211–277` caches `LogFields` per ancestor PID for the request, avoiding duplicate FOXML fetches, but loops through every path occurrence and repeats DC field extraction, MODS identifier XPath, and `LogRecordDetail` construction. `LogFields.java:104–110` computes MODS identifiers on each call. | **Source-derived repeated CPU work**, only when several paths share an ancestor. Its frequency and cost are unknown; preserving per-path log detail may be necessary. | Count paths, unique ancestors and MODS XPath calls per access-log event; compare a per-ancestor computed summary while preserving any required per-path detail and log ordering. |

## Priority and measurement boundary

B11 remains the first search correctness fix because its deployed exception mismatch and two trace-linked spikes are verified. B12 and B13 are logging reliability candidates; confirm the logging durability contract and actual response lifecycle before calling their production impact high. C1 is the smallest low-risk performance pilot in this path, but only if profiling shows material cost. C2 needs path-shape measurements.

The code shows where work can occur. It does **not** identify the critical-path share of logging, the typical ancestor count, a safe async queue design, or a numerical speed gain. The next useful tool pass is JFR/allocation sampling plus dedicated access-log spans in staging, followed by fault tests for Solr logs success/non-200/connection failure and a no-DC FOXML fixture. No production state or application source was changed in this review pass.
