# Folders source audit — persistence and read cost

This source-only pass traced `EndpointFolders`, `FolderDatabase`, and `init_db.sql`. No endpoint or database was exercised. The checked schema may differ from production; verify the deployed schema before estimating affected rows or users. B10 already records the DELETE-trigger count gap.

| ID / priority | Trigger and source evidence | Consequence and confidence | Later validation / fix direction |
| --- | --- | --- | --- |
| B21 / medium | Folder creation calls `db.createFolder` and then `db.createFolderUser(owner)` (`EndpointFolders.java:125–129`). Each method obtains and closes a separate connection after one insert (`FolderDatabase.java:94–121`). | **Confirmed non-atomic sequence in source:** if owner insertion fails, a folder row remains without an owner and will not appear in the owner's `getFolders` query. Incidence unknown. | In the separate benchmarking environment, fail the owner insert after folder creation; inspect rows and retry behavior. Create both rows in one transaction, with an ownership invariant. |
| B22 / medium | Folder deletion calls `deleteFolderUsers` and `deleteFolder` only (`EndpointFolders.java:267–270`). The schema declares `folder_item.folder_uuid` without a foreign key or cascade (`init_db.sql:11–16`); no item deletion occurs in these calls. | **Confirmed orphan-row path for the checked schema:** deleting a nonempty folder leaves its `folder_item` rows. If the deployed schema has extra constraints/triggers, behavior may differ. | Compare `folder_item` rows before/after deletion in an isolated schema matching deployment. Add a transaction with item cleanup or a validated foreign key/cascade; reconcile existing orphans. |
| B23 / medium | `addFolderItems` snapshots `itemsPresent` once, then inserts each request entry separately without updating the set (`EndpointFolders.java:313–325`). `folder_item` has primary key `(folder_uuid,item_id)` (`init_db.sql:11–16`). | **Confirmed duplicate-input failure path:** `{"items":["x","x"]}` for an absent item attempts the same insert twice. The first insert can commit and the second throws, leaving a partly applied request. Different later DB failures have the same partial-commit problem. `removeFolderItems` also uses a stale snapshot and can report a duplicate removal twice (`EndpointFolders.java:374–385`). | Validate duplicate and mid-batch-failure behavior in the separate environment. Deduplicate and validate request IDs, then execute each batch in one transaction; define response semantics for already-present and repeated IDs. |

The folder-list read has an evident N+1 query shape: `FolderDatabase.getFolders` fetches all folders for a user and calls `getFolderUsers` with a fresh connection for every row (`FolderDatabase.java:39–50,74–87`). Measure folder count per user, SQL calls, DB connection wait, and endpoint p50/p95 before considering one join or batched user lookup. The same pattern exists in `getAllFolders`. This is an **unmeasured bottleneck candidate**, not evidence of a slow production endpoint.

`getFolder` reads a folder and its items by UUID without a membership check (`EndpointFolders.java:69–101`). The source comments explicitly describe an anonymous view of owner information, so the intended folder visibility policy must be established before treating this as an authorization defect. The handlers use `JSONObject.append` for arrays (`EndpointFolders.java:56,90,99`), which produces an array containing the supplied array under ordinary `org.json` behavior; confirm the API contract and current clients before changing response shape.

Handoff for the benchmarking environment: measure folder-list query count versus folder count, use representative follower counts, verify count freshness after add/remove (B10), and inspect orphan/ownerless rows after isolated mutation failures (B21–B23). These correctness checks should precede any folders service extraction. No tests or application code were added in this pass.
