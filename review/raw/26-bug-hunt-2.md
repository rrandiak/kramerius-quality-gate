# Bug hunt 2 — independent reliability and boundary review

## Method

This independent pass used `git grep` over Kramerius `origin/master` (`560676c85d276bd53f2dbaae95e87ddc6abd6e07`), Akubra `51d821b`, process-platform `976dc4b`, web client `967fa034`, admin client `cb16f71`, and the MZK chart `46a6479`. I read the existing bug index and audits first, then traced import, delete-tree, processing-index, CDK reharvest, lock, HTTP-client and PDF paths through their callers. Searches covered distributed lock calls and leases, synchronized blocks, XML factories, temporary files, HTTP response closure, thread creation, and broad catches. This was a targeted source audit, not complete coverage of every endpoint or plugin. All cited lines below were reread from the named Git objects; deployed image revisions are unverified. No production request or mutation was made.

## Checked and found clean within the traced paths

- Akubra's `AkubraDOManager.doWithLock` releases an acquired Hazelcast lock in `finally` (`AkubraDOManager.java:430–438@51d821b`). I found no lock-release omission in this method. Lock hold duration and lease sufficiency still need runtime evidence.
- The import worker's `ManagerClient.scheduleSubProcess` closes its HTTP response with try-with-resources and throws on non-success or transport errors (`ManagerClient.java:151–159@976dc4b`). H1 arises in the import caller's catch.
- `Import.run` closes its `CloseableHttpClient` with try-with-resources (`Import.java:207@560676c`), and `Import.ingest(File)` closes its file input stream (`Import.java:692–699@560676c`).
- The CDK delete-library plugin propagates batch-update errors rather than logging and continuing (`CDKDeleteLibrary.java:94–111@560676c`).
- The public PDF resource releases its generation semaphore in `finally` for the reviewed routes (`PDFResource.java:343–345,448–451@560676c`). This is only a semaphore check, not a conclusion about PDF file and stream lifetimes.
- The license process collects per-object errors and throws after its add/remove loop (`SetLicenseProcess.java:103–154@560676c`); I found no silent job-success path in those catches.
- The process-platform manager client closes its response around sub-process scheduling (`ManagerClient.java:151–159@976dc4b`); the import caller is responsible for the result handling.
- The user-profile save method logs and swallows SQL errors, but its only identified servlet caller is commented out of `web.xml` (`ProfilesServlet.java:85,122@560676c`, `web.xml:298–303,450–451@560676c`); I did not promote this inactive path.
- Akubra creates a new DOM serializer for each `DomUtils.toString` call; the synchronized factory method does not share a mutable serializer between callers (`DomUtils.java:427–441@51d821b`).
- Akubra's shared date formatter serializes both parse and format operations (`SafeSimpleDateFormat.java:33–42@51d821b`); I found no unsynchronized use through this wrapper.

The Akubra lock method at this pinned revision is `doWithLock`, using a timed Hazelcast lock and `finally` unlock (`AkubraDOManager.java:406–438@51d821b`). The MZK values' public-pod instrumentation list names `doWithReadLock` and `doWithWriteLock`, but not `doWithLock` (MZK deployment values). Because the deployed Akubra image may differ, this is a measurement caveat rather than a confirmed production telemetry defect. The source review found long operations inside some PID-lock callbacks, but it did not establish lock hold percentiles, configured lease values, or a deadlock; those are not reported as public defects.

## Performance follow-up from read-only production aggregates

The mounted gateway configuration has four proxy-cache rules, including search and thumbnails, and no IIIF cache rule. In a warm five-hour window, complete gateway logs recorded 68,079 successful search GETs and 183,138 successful thumbnail GETs. A method-matched OTel estimate, weighted according to the collector's one-percent fast-trace sampling policy, estimated 58,669 ±4,712 and 119,668 ±6,773 corresponding backend 200 responses. That suggests the existing gateway cache already avoids roughly 14% of search and 35% of thumbnail backend requests, with approximate sampling margins of seven and four percentage points respectively. These are estimates, not observed cache HIT counts; the deployed access-log table has no cache-status column, and direct backend traffic or tail-sampling behavior could bias the comparison. A first estimate was discarded because it mistakenly included search OPTIONS spans while comparing with gateway GETs.

The thumbnail cache occupied about 176 MiB against its configured 768 MiB maximum, while the search cache occupied about 64 MiB against its 64 MiB maximum. Occupancy alone cannot show useful-entry eviction because expired files can remain on disk. Exact-URI reuse after the first two successful requests was 37.8% for thumbnails and 20.4% for search within one-minute URI groups, so the estimated thumbnail savings are close to its observed reuse opportunity; search may have some remaining headroom, but this check does not identify the cause. Direct IIIF non-`info.json` responses had 120,426 requests after the first two uses (39.4% of that route's successful GETs), while forwarded non-`info.json` responses had only 165 (0.3%). These figures are traffic-shape evidence only; no shared IIIF cache change is proposed here.

In 180 days of process history, 622 FINISHED delete-tree jobs had a median run time of 24.4 seconds, p90 709 seconds, and maximum 8,404 seconds. Three FINISHED FOXML-import jobs had a median 182.1 seconds. Object counts were unavailable, so these durations cannot establish per-object cost or attribute slow jobs to any specific source path. A warm five-hour query returned no requests for the legacy image servlet routes reviewed for monitor contention; that source lead is not a current traffic priority.
