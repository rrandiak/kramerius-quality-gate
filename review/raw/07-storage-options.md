# Run 07 — Akubra storage, grouping, compression, and S3

## Current source contract and evidence limits

The checked-out Akubra source creates separate filesystem blob stores for object XML and managed datastreams, wraps each with an ID mapper, and enables safe replacement for both (`AkubraDOManager.java:118–128`). The default configuration maps identifiers into MD5-derived `##/##` directories (`configuration.properties:508–511`; `HashPathIdMapper.java:88–129`). This layout spreads files by identifier; it does not group related objects. Production was observed using NFS-class object/datastream mounts in Run 01, but the deployed Akubra revision, effective patterns, occupied bytes, inode counts, and actual NFS performance are not verified.

Akubra reads an object by streaming its stored XML into JAXB; it can also return the raw XML bytes. Datastreams are retrieved as streams (`AkubraDOManager.java:130–169`). The low-level interface supports add, replace, remove, point read, existence, size, and iteration over all object and datastream keys (`AkubraLowlevelStorage.java:135–206`). A caller can seek in neither interface shown here; a replacement backend must still preserve streaming and bounded memory on large datastreams. Listing must return logical keys even if physical storage is compressed or bundled.

An object write marshals the whole `DigitalObject`, may write managed datastream data, then adds or replaces the object XML (`AkubraDOManager.java:231–260,385–406`). Deletion can remove managed datastream versions before the object (`AkubraDOManager.java:172–229`). There is no transaction across the object XML, datastream files, and processing index. The current safe-overwrite path writes a `new` blob, moves the original to `old`, moves `new` into place, then deletes `old`; recovery is attempted for some failed moves (`AkubraLowlevelStorage.java:322–396`). This is a *required behavior to reproduce and failure-test*, not proof of full atomicity or crash safety on the production NFS. The source has an optional per-PID Hazelcast lock with configured wait and lease (`AkubraDOManager.java:405–439`); whether it is active across production writers is unverified. The low-level code says audit/rebuild must happen out of band (`AkubraLowlevelStorage.java:235–244`).

Source inspection also found a correctness risk for Run 04: `AkubraDOManager.write`, `deleteStream`, and `deleteObject` log some storage failures and return normally (`AkubraDOManager.java:172–260`). In `CoreRepositoryImpl.delete`, this may allow processing-index deletion and commit after the object removal failed (`CoreRepositoryImpl.java:136–162`). Reproduce with injected I/O failure before treating it as a production defect. Any storage migration needs a reliable error contract and reconciliation, otherwise a benchmark can appear successful while losing updates.

## Options to compare independently

| Option | Read and write implications | Space, inode, and recovery questions |
| --- | --- | --- |
| Current per-object/per-datastream files on NFS | Baseline point reads and streaming; one logical blob maps to one file. Whole XML is rewritten on object update. | Measure actual allocated bytes, inodes, metadata operations, retransmits, and restore time; NFS server behavior may dominate. |
| Parent-based directories, files unchanged | Only path mapping changes. Each read still opens an individual file; a child's parent must be known or mapped before lookup. Reparenting needs a move or stable indirection. | File/inode count stays approximately the same. Directory locality may help or hurt; large parent directories and parent/foster links need explicit handling. Do not present this as a storage-compression design. |
| Per-object zstd on object XML | Encode on write and decode on read, preserving one logical key/file. Versioned format or header plus fallback is needed to read existing uncompressed blobs. Keep managed datastreams separate for the first test. | Measure XML compression ratio, decode/encode CPU, memory, cold/warm latency, backup size, and mixed-version recovery. Inodes do not fall. Already-compressed or large binary datastreams must be sampled separately, not assumed compressible. |
| Physical parent bundles, uncompressed | A logical-key index maps each PID to a member. Random reads may require range reads or more bytes; one member update may rewrite a bundle or append and compact it. Parent and foster relationships need a canonical grouping rule. | Could reduce physical file count, but adds index/manifest files, write amplification, compaction, concurrent-update coordination, tombstones, and restore complexity. Quantify by parent-size distribution, not an average alone. |
| Compressed parent bundles | Combines bundle lookup and compression. Independent frames/indexes may preserve point reads; one compressed stream per bundle can amplify reads and rewrites. | Evaluate only after per-object compression and uncompressed bundling separately. Measure compressed bytes, read amplification, CPU, compaction, and crash recovery. |
| Object-per-key S3-compatible backend | Replace/adapt the blob store and mapping. Point reads and streaming are plausible, but the current `moveTo`-based replacement cannot simply be assumed equivalent. Define logical publish/version semantics and key listing. | Benchmark request counts, transfer, concurrency, tail latency, retries, partial failure, consistency, backup/restore, and ongoing storage/request/transfer costs in the intended network placement. Test object XML and datastreams separately. |
| Hybrid filesystem/object storage | Keep the more latency-sensitive or frequently rewritten class on NFS and move the other class after measurement. | Adds two operational paths and failure modes; compare total cost and recovery rather than only capacity pricing. |

Parent grouping is especially ambiguous in this model: parent/child and foster relations may be multiple or mutable. Define the canonical owner and mapping independently of the relationship graph before any migration. A directory scheme that requires a parent lookup to locate a child can add a dependency to every point read. A bundle must expose a stable logical PID lookup regardless of reparenting, orphan objects, and large groups.

## Compatibility and failure gates

| Contract | Test before accepting any new layout/backend |
| --- | --- |
| Key identity and listing | Every object and managed datastream key round-trips; `listObjects`/`listDatastreams` enumerate logical keys exactly once through old, new, and mixed formats. |
| Point read and streaming | Validate complete bytes/checksums, bounded heap and open handles, short reads, slow consumers, cancelled streams, large datastreams, and concurrent readers during writes. |
| Replace and delete | Test create/replace/delete, existing and missing keys, concurrent same-PID and cross-PID updates, and stale writer after lock lease expiry. Define read visibility before, during, and after publish. |
| Crash/recovery | Inject failure at each write, rename/publish, manifest, datastream, and cleanup step; restart writers/readers; reconcile orphans and partial object/datastream pairs. Prove backup and restore can recover a consistent key set. |
| External index | Reconcile Akubra logical keys and versions with the processing index after failed writes, deletes, and interrupted migration. Do not use index visibility as proof of stored bytes. |
| Operations | Establish monitoring, corruption detection, repair/rebuild, restore drill, version rollback, and an explicit migration/cutover method. Measure these with the same data shape as the pilot. |

For S3-compatible storage, first implement a small adapter experiment behind the Akubra blob-store boundary or a revised low-level storage interface. Specify whether conditional writes, immutable versioned keys plus a manifest, or another publish protocol supplies the update semantics. Verify them against the chosen service; do not assume filesystem rename or NFS lock behavior exists. The adapter must propagate errors, close streams, paginate listing, distinguish missing keys from transient errors, and prevent stale writers from publishing after a newer version. A local S3 emulator can check protocol handling, but latency and failure benchmarks require the intended region/network and service configuration.

## Measurement run and effect estimates

1. **Inventory a representative copy.** Record deployed revision/configuration and all writers. On an authorized storage snapshot, stratify object XML and managed datastreams by byte size, content type, parent/group size, depth, foster links, and hot/cold access. Measure logical bytes, allocated bytes, file and directory counts, open/stat/list operations, write/delete frequency, and backup/restore time. Capture a repeatable PID/key manifest with checksums. Log-based endpoint classification is manually curated; use it to choose workload classes, not to infer storage reads without traces.
2. **Measure present behavior.** Under normal image-opening, search, indexing, import, and background-job traffic, collect Akubra point-read/write/list rates and p50/p95/p99, bytes transferred, XML parse time, CPU/GC, NFS client and server IOPS/latency/retransmits, and job throughput. Trace representative paths to tell whether an image or search request actually reads FOXML/datastreams. Run 05's indexing stage measurements supply the import/index baselines. Keep dependency outages, including Solr downtime, separate from storage latency.
3. **Run isolated format tests.** Compress a stratified copy of object XML at selected zstd levels and verify exact round-trip. Compare per-object read/replace with current files under cold and warm caches, with serial and bounded concurrent reads. Separately prototype uncompressed parent bundles with a key index and mutation/recovery tests. Measure physical bytes, inode/metadata count, CPU, peak memory, read bytes per logical read, and bytes rewritten per logical update. Only then test compressed bundles if either individual option warrants it.
4. **Run S3 semantics and placement tests.** Using the same manifest and read/write mix, compare NFS and an S3-compatible adapter in the intended placement. Measure successful operations/s, p50/p95/p99, transferred and billed bytes, request types/counts, connection pool waits, error/retry rates, concurrent-reader visibility, and repair time during injected failures. Include small hot XML and large streaming datastreams separately. Repeat with backup/restore and a full consistency check.
5. **Replay user-visible work.** Re-run the same index/import jobs and representative image openings and searches while changing one storage variable at a time. Report indexing objects/s and end-to-end job time; image time to first metadata/image and request p95/p99; search p95/p99 and successful throughput. If a search path does not touch Akubra, report no direct storage effect and check only concurrent resource contention. Record NFS/object-store, Solr, CPU, and heap load so a faster microbenchmark is not mistaken for a faster user flow.

For each option, compute object-XML savings as `(baseline physical object-store bytes − candidate physical object-store bytes) / baseline physical object-store bytes`. Compute whole-repository savings separately with both object and datastream bytes in the denominator, including manifests, indexes, replicas, temporary rewrite headroom, and backups as applicable. Compare ongoing cost as storage capacity plus requests/metadata operations, network transfer, compute, backups, and operational work over an explicit retention and workload horizon. No representative sample, price schedule, or end-to-end benchmark is available yet, so there is **no numerical savings or speed estimate**.

## First pilot, decision, and missing access

The smallest format pilot is **per-object zstd on an isolated, checksum-verified copy of object XML**, with mixed old/new reads, update/delete, failure injection, and a fixed image/index workload. It isolates byte and CPU tradeoffs without imposing parent-group semantics. It is an experiment, not a recommendation to deploy compression. In parallel only as a design exercise, specify the S3 publish protocol and bundle key index; implementation should follow measured need and the compatibility gates.

Choose among retaining NFS, changing layout, per-object compression, bundling, S3, or a hybrid only after the above results show a material end-to-end benefit under correct update/recovery behavior. A storage decision cannot be derived from compression ratio, inode count, or object-store price alone.

The implementing team needs read-only access to production configuration and revisions; an authorized, anonymized storage snapshot or stratified FOXML/datastream sample with parent relations; NFS and storage metrics; Akubra read/write/list tracing; representative indexing/import jobs and interactive request traces; a staging NFS environment and S3-compatible target in intended network placement; fault-injection and backup/restore capability; and service pricing/retention assumptions. None of the storage sample, controlled benchmarks, S3 adapter, or failure tests has been run in this source review.
