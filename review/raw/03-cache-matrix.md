# Run 03 — cache inventory and invalidation matrix

This is a source-based inventory from the checked-out Kramerius and Akubra repositories, not a measured cache proposal. The deployed Kramerius revision and cache configuration are still unverified. There is no production hit-rate, object-size, write-rate, or NFS cost sample yet. Public request counts in [Run 01](01-baseline.md) establish possible exposure, not the number of cacheable reads.

## Readers and writers that define freshness

The source has separate whole-object and datastream reads. Request-time Solr access logging reads a whole FOXML DOM for each distinct PID in a path (`SolrStatisticsAccessLogImpl.java:224`), while direct and forwarded IIIF use `IIIFUtils.iiifImageEndpoint` to read a RELS-EXT-derived tiles URL (`IIIFUtils.java:33`). Client item endpoints read MODS, DC, OCR, image and other datastreams (`ItemsResource.java:383`, `429`, `478`, `1927`); item export reads a whole FOXML DOM (`ItemsResource.java:1037`). Search indexing reads whole FOXML (`Indexer.java:257`) and selected datastreams. These consumers have different sizes, sensitivity, and reuse; a single whole-FOXML cache should not be assumed best.

Known write families in the checked source include Akubra `ingest`, object `delete`, XML/managed/external datastream create/update/delete (`AkubraRepository.java:47–302`); legacy import updates and deletes (`Import.java:553`, `560`, `645`); admin object/datastream edits and deletes (`ItemsResource.java:465`, `751–773`, `883`; `AkubraResource.java:255–376`); collection edits (`CollectionsResource.java:351`, `410`, `1057`, `1136–1312`); and index updates/reindexing (`Indexer.java:584` for a commit boundary). Worker plugins, direct Akubra consumers, and external tools must be included before claiming complete write coverage. A RELS-EXT or parent-child update can affect more than one PID's derived entry; a rights or license update can affect public visibility and user-specific results; deletion must evict object and derivative entries. An index commit changes search-result freshness even if Akubra FOXML is unchanged.

No cross-process invalidation protocol was identified from the cache classes reviewed. That is a **coverage limit**, not proof none exists elsewhere. Two public pods and separate workers mean a local eviction in one JVM would not update the others. TTL bounds staleness but does not provide immediate read-after-write consistency.

One concrete defect candidate belongs in Run 04: `CDKRequestCacheSupportImpl.remove(CDKRequestItem)` formats a string column name (`ID_COLUMN = "id"`) with `%d` at line 104. If invoked, Java formatting should throw before executing the delete. No call site was found in the focused source search, so runtime impact is unknown.

## Candidate matrix

Priority here is the order to **measure and validate**, not an implementation ranking. Capacity values are to be sized from sampled bytes and reuse traces; none is estimated from request totals.

| Priority / candidate | Key and scope | Freshness and invalidation requirement | Workload effect to measure / gate |
| --- | --- | --- | --- |
| 1. Audit existing Solr and rights caches | Existing PID key and rights key; local JVM | Record effective TTL, hit/miss/eviction and stale-read window. Test updates, deletes, permissions, and parent/path changes across two pods. Fix key or invalidation semantics before increasing capacity. | Direct IIIF and CDK source lookup latency, search authorization, correctness after admin changes. No new cache until the existing behavior is understood. |
| 2. Cache only RELS-EXT-derived tiles URL | `(PID, object or RELS-EXT revision)` within each public JVM, if Akubra exposes a trustworthy revision; otherwise PID plus explicit distributed invalidation. Bound by measured bytes/reuse. | Invalidate after RELS-EXT update or object delete; update ordering must precede the next successful response. A TTL-only variant needs an explicit accepted stale period. | Measure Akubra read/parse frequency and time for direct/forwarded IIIF metadata and tiles. Compare page-opening latency and NFS load under warm/cold cache. |
| 3. Reuse parsed FOXML or selected parts during access-log enrichment | `(PID, object revision)` for a read-only parsed projection, with bounded per-process memory; consider request/job-local reuse first. Avoid sharing mutable DOM nodes. | FOXML/XML datastream writes and delete invalidate. Parent-path changes require rebuilding the path-derived record even when the child's FOXML is unchanged. Request-local reuse needs no cross-request invalidation if all reads are from a coherent snapshot; confirm that assumption. | Count repeated ancestor reads and parsing in `reportAccess`, then compare `info.json` critical-path cost and NFS reads. This may overlap with Run 02 logging redesign. |
| 4. Improve CDK `query_cache` lifecycle | Existing `(source, URL, PID, user)` dimensions, with explicit query/permission variants; DB scope spans pods. | Reharvest/source changes, PID deletion, rights change, and user/session expiry need targeted invalidation or bounded freshness. Verify existing `removeByPid` callers and cleanup before adding payload classes. | Compare remote-call avoidance, response latency, DB load, stale-response incidence, and reharvest lag for client/CDK traffic. |
| 5. Search response caching | Canonical query, filters, sort, page, index generation, and authorization context; shared cache only if security rules permit. | Refresh or version on index commit; invalidate for permission/collection changes. Do not cache errors from Solr downtime as successful data. Prefer existing Solr filter/query cache when it covers the same reuse. | Segment search classes; measure query repetition, Solr cache metrics, hit rate, memory, stale windows, search p50/p95/p99, and indexing visibility delay. |
| 6. Whole-FOXML cache | `(PID, object revision)`; bounded local or shared storage based on measured sizes. | Every object/datastream mutation, delete, and relevant relationship change must select a new version or invalidate across all readers. Mixed revisions within one request need handling. | Compare whole-object bytes/read and parse CPU for indexing, export, and access logging; account for memory, NFS reduction, write pressure, and extra version lookup. Proceed only if whole-object reuse beats narrower projections. |

Content-addressed or immutable datastream bytes **could** avoid explicit write invalidation when the cache key is the content hash or immutable version and every update changes that key. This is a design option, not a verified Akubra property. A process/job-local cache could also avoid cross-process invalidation only if the job reads an immutable snapshot or prevents concurrent writes; neither condition has been established. Every proposed cache therefore needs a declared owner for invalidation and an explicit failure behavior when invalidation delivery is delayed.

## Measurement and decision run

Instrument each candidate read with route/job class, cache hit/miss, bytes, parse CPU, dependency elapsed time, object version, and anonymous PID cardinality buckets. Measure representative warm/cold intervals and an LRU replay for plausible capacities; record total heap/off-heap use and eviction. Pair a controlled staging read workload with mutations: MODS/DC/RELS-EXT update, permission/license change, parent-child relink, object/datastream delete, bulk import, reindex and index commit. Read from both public pods and a worker before and after each mutation, measuring stale duration and correctness. Include external/direct writer paths in coverage or state that such writes require a reconciliation mechanism.

For each surviving candidate, compare indexing documents/s and visibility delay, image-opening page time and request p50/p95/p99, or search latency/throughput under identical load and cache state. Report absolute differences, relative differences, variance, memory and write amplification. Keep effects separate where a cache and asynchronous logging remove the same FOXML read. Until these measurements and invalidation paths exist, **no speed or space gain is assigned**.
