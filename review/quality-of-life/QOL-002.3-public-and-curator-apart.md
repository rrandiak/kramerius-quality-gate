# QOL-002.3 — Level 3: run public and curator with only their own code, first by a runtime role switch, then as separate images, with an all-in-one stack for CI

> **In one sentence:** the third level of [QOL-002](QOL-002-modularize-in-four-levels.md): block admin routes on public
> pods at once, then let each pod bind only its role's resources (`KRAMERIUS_ROLES`, as `cdk.server.mode` already does
> for the CDK), and once level 2's modules exist build a public image without curator code and a curator image without
> public-only code, plus an all-in-one Compose stack for developers and CI.

## Today

- MZK runs public and curator as separate deployments of the **same image**; only the gateway routes `/search/api/admin/`
  to curator ([deployment check](../raw/11-deployment-incident-check.md)).
- `ApiServletModule.configureServlets` binds every resource in every pod; admin resources start at line 182
  (`rest/.../api/guice/ApiServletModule.java:182`).
- **The pattern already exists:** `cdk.server.mode` (line 103) decides which CDK resources are bound (lines 104–105,
  150–153).
- No Compose stack runs Kramerius, the process manager, a worker, Solr and PostgreSQL together.

## Questions and answers

### Q1. Runtime switch or separate images?

**Answer:** both, in that order. The runtime switch needs only level 1 and helps at once; separate images need level 2's
modules ([QOL-002, Q4](QOL-002-modularize-in-four-levels.md#q4-public-and-curator-separated-at-runtime-or-at-build-time)).

### Q2. What does each role contain?

| Role | Resources | Feature modules (level 2) |
| --- | --- | --- |
| **public** | client API v7, IIIF, OAI, legacy K5 client API, folders | kernel, `rights` (evaluation), `users`, `documents` (until level 4), `statistics` (capture), `folders`, `uiconfig` (read) |
| **curator** | admin API v7 (items, collections, rights, users, licences, config, UI config, processes, reharvest) | kernel, `rights` (evaluation and administration), `users`, `collections`, `process-client`, `uiconfig`, `workmode` |
| **cdk** | `apiNew/cdk`, CDK client resources | kernel, `cdk`, `rights`, `users` |

Default `KRAMERIUS_ROLES=public,curator`, so a library running one pod sees no change.

### Q3. Is the CDK a role or a separate build?

**Answer:** a role of the same build, as it is today through `cdk.server.mode`; `KRAMERIUS_ROLES=cdk` replaces the flag.
**Why:** the CDK shares the kernel, rights and users; a separate build would duplicate them.

### Q4. Why an all-in-one stack in this level?

**Answer:** because splitting roles needs a test that every route answers in the right role, and that test needs the whole
system running. The same stack serves developers and small libraries.

## Proposal

1. **Routing hardening** (smallest, first): an in-app filter answers 404 for `/search/api/admin/*` on pods without the
   curator role; the chart adds the same rule to the ingress.
2. **Runtime role switch:** split `ApiServletModule` into a core module plus one Guice module per role; install those in
   `KRAMERIUS_ROLES`; `cdk.server.mode` maps to the `cdk` role.
3. **All-in-one Compose stack** around today's images: Kramerius (all roles), process manager, one worker with all
   plugins, Solr with the shipped configs, PostgreSQL, the lock server, a small test data set; run in CI.
4. **Per-role images** once level 2 exists: one WAR per role assembled from its modules; the all-in-one image keeps them
   all.

## What gets easier

| Who | Today | After | Basis |
| --- | --- | --- | --- |
| operators | admin endpoints are bound in public pods; only the gateway keeps them out | 404 in the app (step 1), not bound (step 2), absent (step 4) | `ApiServletModule.java:182` |
| developers and CI | integration tests need a cluster | `docker compose up` | packaging |
| small libraries | the MZK-style multi-deployment setup or a hand-made one | one stack | packaging |

No latency change: public and curator already run in separate pods.

## Costs and risks

- Some resources may be needed by more than one role; the role assignment must be tested route by route.
- Per-role images add build and test work.

## Alternatives

1. **Only routing hardening.** Small, worth doing first; leaves admin code bound in public pods.
2. **Separate images without level 2.** Would mean excluding classes by hand from one module; fragile.

## Effort

**Size: L**, set by a configuration contract (`KRAMERIUS_ROLES`) and several modules.

| Part | Size | Why this size |
| --- | --- | --- |
| Admin-route filter and ingress rule | S | one filter, one rule |
| `ApiServletModule` split, `KRAMERIUS_ROLES` | M | many bindings, per-role smoke tests |
| All-in-one Compose stack in CI | M | packaging, test data, CI job |
| Per-role images | M | after level 2: assemblies and their CI |

## How we know it worked

- Per-role smoke test on the Compose stack: every admin route returns 404 with `KRAMERIUS_ROLES=public`, every client route
  with `curator`.
- The public image's class list has no `apiNew.admin` classes (step 4).
- The integration suite runs in CI in under 15 minutes.

## Open questions

- Which CDK resources belong to which role? `CDKProcessResource` sits in the admin package but serves the CDK.
- Do other libraries run public and curator separately, or one pod for both?
