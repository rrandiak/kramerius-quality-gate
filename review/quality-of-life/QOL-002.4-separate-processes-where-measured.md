# QOL-002.4 — Level 4: move only coarse, rare or asynchronous parts into separate processes, starting with the statistics writer, and only with a measured need

> **In one sentence:** the last level of [QOL-002](QOL-002-modularize-in-four-levels.md): once levels 2 and 3 have
> given modules clean boundaries, run the statistics writer as one process for all public pods and keep document
> generation off the web image, and turn folders or the repository into services only when load, release cadence or
> ownership measurably require it.

## Today

- The access log writes synchronously in the IIIF path, in each public pod: one Solr POST and ~3 FOXML reads per
  `info.json` ([PM-003](../perf-medium/PM-003-batched-access-log-writer.md)).
- Selection PDFs render in the public web JVM ([BUG-015](../bugs/BUG-015-pdf-font-scan-per-request.md)); full PDFs, e-books
  and text already run as `public-worker` jobs.
- Folders: a few calls per session, own tables, public only.
- Repository: every public request and ~4 FOXML reads plus 2 processing-index queries per indexed page.

## Questions and answers

### Q1. What may run as a separate process?

**Answer:** a part may leave the JVM only if its calls are rare, coarse or asynchronous, so a network hop costs little and
a failure can degrade one feature instead of reading:

| Part | Verdict | Why |
| --- | --- | --- |
| rights | **stays in-process** | every image, tile and item request; ~26 ms per check warm, already half of a direct IIIF request ([PS-002](../perf-simple/PS-002-rights-check-refetches-solr-doc.md)) |
| repository reads | **stays in-process** now | a remote call per read multiplies round trips; a service only with batched calls |
| statistics writing | **separate, asynchronous** | every `info.json`; readers should never wait for it |
| document generation | **separate** (workers) | on request, heavy, already partly on workers |
| folders | **may be separate** when a reason appears | a few calls per session |

### Q2. How does the statistics writer work?

**Answer:** public pods capture the access event (PM-003's capture step) and publish it to a durable queue; one writer
replica batches all pods' events (one Solr `logs` POST per batch), keeps one ancestor cache for enrichment (the FOXML reads
were ~68 ms of the logging cost in the first measurement), and restarts on its own. When it fails, events wait in the
queue or are dropped by an explicit policy; readers do not notice.
**Which queue:** a PostgreSQL table needs no new infrastructure; a Redis stream fits where Redis already runs (MZK, for the
gateway).

### Q3. When does a module become a service?

**Answer:** only with a measured reason (load, release cadence, a team that owns it), and with batch calls, timeouts and a
defined fallback. Candidates, in order:

1. **Folders**, if folders are ever shared across libraries through the CDK or need their own release cadence.
2. **Repository service** together with [PH-003](../perf-hard/PH-003-storage-backend-options.md): owns FOXML, relations and
   locks in PostgreSQL, offers batched reads (a node and its children, a page range with prefetch as in
   [PM-001](../perf-medium/PM-001-read-once-then-prefetch.md)) so indexing does not pay a round trip per object. With one
   owner of the repository, cross-JVM locks shrink to one place.

## Proposal

1. Statistics capture, queue and one writer (PM-003 plus a queue).
2. Selection PDFs as `public-worker` jobs, or at least the `documents` module out of the public image (level 2 makes it
   possible).
3. Folders and repository as services only after the measurements in "How we know it worked".

## What gets easier

| Who | Today | After | Basis |
| --- | --- | --- | --- |
| readers of the site | a slow or failing statistics write or PDF render shares the reader's JVM or request | unaffected | source |
| operators | statistics cost scales with public pods | one writer, one cache, batched writes | PM-003 first measurement |

## Costs and risks

- A queue is new infrastructure for libraries without one (a PostgreSQL table avoids that).
- Every service adds deployment, monitoring and a failure mode; identity and rights must be propagated to it.
- A repository service needs PH-003's benchmark and data migration first.

## Alternatives

1. **Stop at level 3.** Fine for most libraries; the statistics writer still runs inside each public pod.
2. **Services now.** Rejected by Q1: network hops on the hottest paths.

## Effort

**Size: XL**, set by new deployables and, for the repository, a migration.

| Part | Size | Why this size |
| --- | --- | --- |
| Statistics capture, queue and writer | M | PM-003 plus a queue |
| Documents off the web image | M | selection PDF as a job, or module out of the image |
| Folders service | L | new deployable, identity propagation |
| Repository service with PH-003 | XL | new system, data migration, all callers |

## How we know it worked

- With the statistics writer stopped for an hour on staging, `info.json` latency and errors do not change, and the queued
  events are written afterwards.
- Folders: extract only if load or release pressure is shown after level 3.
- Repository: PH-003's benchmark must show batched service reads at least as fast for the indexer's node build (~110 ms p50
  today) as in-process reads.

## Open questions

- PostgreSQL table or Redis stream for the statistics queue?
- Would a repository service also serve other libraries' CDK harvests?
