# QOL-002.1 — Level 1: give each caller only the interface it needs, so readers cannot write and only the indexer writes Solr

> **In one sentence:** the first level of [QOL-002](QOL-002-modularize-in-four-levels.md): put narrow interfaces between
> Kramerius code and its stores (a repository reader, a repository writer, an index writer, a rights contract), hand
> each caller only the one it needs, break the package cycles in `shared:common`, and enforce it with architecture tests,
> without changing behavior, build or deployment.

## Today

See [QOL-002, Q2](QOL-002-modularize-in-four-levels.md#q2-does-kramerius-need-more-interfaces). In short, at Kramerius
`560676c`:

- Services are already injected by Guice; the 105 `new …Impl(` calls are value objects. The problem is not missing
  interfaces but **wide** ones.
- Public API, CDK API and the search WAR use 14, 5 and 8 distinct Akubra methods, **all reads**, but receive the whole
  read/write `AkubraRepository`.
- Admin handlers call 11 distinct raw write methods (47 calls), including `pi().commit`, `re().update` and `doWithLock`; plugins
  15 (49 calls).
- Admin handlers write Solr next to the indexer (`SearchIndexHelper`, `ItemsResource.deleteFromSearchIndex`,
  `CollectionsResource`).
- `SecuredAkubraRepositoryImpl` (repository plus rights checks) is in the `security` package, so security and repository
  depend on each other.
- Package cycles: `security` ↔ `service`, `security` ↔ `users`, `security` ↔ root package; `utils` imports `service`,
  `document`, `solr` and `impl` through `DCUtils`, `IterationUtils` and `utils/solr/SolrUtils`.

## Questions and answers

### Q1. Where should the new interfaces live: in Akubra or in Kramerius?

| Option | For | Against |
| --- | --- | --- |
| In Akubra | every user of Akubra gets them | needs an Akubra release and agreement before anything moves |
| **In Kramerius first**, as interfaces implemented by delegating to `AkubraRepository` | no release needed; can be tried module by module | a second layer until Akubra adopts it |

**Answer:** Kramerius first, then propose the same interfaces upstream once they have settled.

### Q2. What does the writer offer: today's raw methods, or intent-level operations?

**Answer:** start with the raw subset that writers use today (same calls, narrower type), and replace them with
intent-level operations (`replaceDatastream`, `setRelations`, `deleteObject` with explicit effects) as
[QOL-007](QOL-007-one-implementation-per-curator-write.md) lands.
**Why:** narrowing first is a pure refactor that tests can prove; changing what writes do is a behavior change and belongs
in QOL-007.

### Q3. How are the rules kept?

**Answer:** architecture tests (ArchUnit) in the build. A rule that is not tested erodes with the next feature.

### Q4. How are the cycles broken?

**Answer:** by moving each class to the side that uses it, not by adding interfaces:

| Cycle | Move |
| --- | --- |
| `utils` → `service`, `document`, `solr`, `impl` | `DCUtils`, `IterationUtils`, `SolrUtils` go to the feature that uses them (documents, indexer); `utils` keeps only code with no Kramerius imports |
| `security` ↔ repository | `SecuredAkubraRepositoryImpl` becomes a repository decorator outside `security`, using the rights contract |
| `security` ↔ `service`, `users`, root | the security contract (user, rights decision) moves to its own package; implementations depend on it, not the reverse |
| `security` → `dochub`, `virtualcollections`, `biz` | to examine per class; `virtualcollections` has no users outside `shared:common` |

## Proposal

1. **`RepositoryReader`**: the union of the read methods that public, CDK and the search WAR use; bound in Guice; those
   callers inject it instead of `AkubraRepository`.
2. **`RepositoryWriter`**: the raw write subset, injected only into admin handlers and plugins that write.
3. **`IndexWriter`**: held only by the indexer; `SolrAccess` stays as the index reader. Admin handlers that write Solr
   today keep doing so behind `IndexWriter` until QOL-007 Q3 removes them.
4. **Rights contract** (`RightsEvaluator`: user, PID, path, action → decision) separated from the repository; the secured
   repository becomes a decorator.
5. **Cycles** broken as in Q4.
6. **Architecture tests:** public, CDK and search-WAR classes cannot import `RepositoryWriter`, `IndexWriter` or
   `AkubraRepository`; no package cycle in `shared:common`.

## What gets easier

| Who | Today | After | Basis |
| --- | --- | --- | --- |
| reviewers | any class may write the repository or Solr | only holders of the writer types; a test fails otherwise | design |
| developers | a public resource can call `delete` by mistake | it does not compile | design |
| level 2 | `shared:common` cannot be cut because of cycles | packages can move into modules | source |

No behavior, build or deployment change.

## Costs and risks

- Many files change their imports; merge conflicts with ongoing work upstream.
- A second interface layer over Akubra until upstream adopts it.

## Alternatives

1. **Do nothing.** Levels 2 and 3 stay blocked by cycles and wide access.
2. **Interfaces in Akubra first.** Cleaner end state, but blocked on a release; can follow.

## Effort

**Size: L**, set by changes across several modules.

| Part | Size | Why this size |
| --- | --- | --- |
| `RepositoryReader` and its callers | M | three consumer groups, mechanical |
| `RepositoryWriter` and `IndexWriter` | M | admin handlers and plugins |
| Rights contract and secured-repository decorator | M | `security` package |
| Cycle breaking | M | class moves, imports |
| Architecture tests | S | a few rules |

## How we know it worked

- The architecture tests pass, and fail when a public resource imports a writer.
- `jdeps` or the ArchUnit cycle check shows no cycle between `shared:common` packages.
- The existing test suite passes unchanged (no behavior change).

## Open questions

- Is the union of reader methods small enough to keep as one interface, or should images and text get their own?
- Will Akubra's maintainers take the interfaces upstream?
